How to mark a check

Every check takes one of three marks, or stays blank. Items tagged per theme take a mark for light and a mark for dark, and count as two checks.

MarkMeaningRequired follow-up
PassMeets the criterion on every screen and state you sampled for this item.None.
FailAt least one reproducible instance does not meet it.Severity, a note with the measured value, and an evidence reference.
N/AThe feature does not exist in this app.Say why in the note.
BlankNot reviewed yet.Keeps the verdict at Incomplete. A blank is never a pass.
Limit

A pass is not a conformance claim

A manual review samples screens and states. Passing means you found no failure in what you tested, not that the whole app conforms. Treat the verdict as evidence about the sample.

WCAG items cite a success criterion from WCAG 2.2 at level A or AA and have a measurable pass or fail. Practice items are good-UX checks that WCAG does not require, so they are judgment calls. Use WCAG items only on the Checklist tab for a strict conformance read.

Review flow

Seven steps in a fixed order. Each theme gets its own pass so you never compare one against the other from memory, and keyboard and screen reader checks come last because by then you already know the screens. The loop at the end is the part people skip: every fix is retested in both themes.

#StepWhat you doWhat you end with
1ScopeFill in the review details. List 3 to 6 critical flows on the Test plan tab.Details and flow list
2Set upZoom 100%, extensions off, fresh profile, throwaway data ready, versions noted.Environment notes
3Light passContrast, type, and layout. Sample the worst case on each screen, not the best.Light results
4Dark passRepeat the per-theme items. Hunt for hard-coded colors left over from light.Dark results
5Functional walkKeyboard only, then forms and errors, then navigation, then a screen reader on the critical flow.Functional results
6LogGive every failure a severity, a note with the measured value, and a named screenshot.Findings and evidence
7VerdictApply the suggested verdict, then retest each fix in both themes before closing it.Decision

Set up before you start

Most false results come from the environment, not the app. A browser extension that restyles pages, a cached stylesheet, or a stored theme preference can all make a broken screen look fine or a fine one look broken.

  • Reset browser zoom to 100% and turn off extensions that restyle or block page content, including dark-mode extensions and ad blockers.
  • Use a fresh profile or a private window so a stored theme choice or cached CSS cannot hide a problem.
  • Prepare throwaway data for delete, deactivate, and submit tests, and one account per role you need to cover.
  • Open DevTools and enable the rendering emulations you will need: color scheme, forced colors, reduced motion, and vision deficiencies (see the DevTools reference in the appendix).
  • Write browser and OS versions into the environment notes on the Test plan tab, and name screenshots using the convention on the Findings tab as you take them.
Method

Do the theme passes separately

Finish every per-theme item in light, then repeat them in dark. A screen that passes in light can fail in dark for unrelated reasons, such as a brand accent that only works on one background, so a quick side-by-side glance is not a substitute for measuring each theme.

The calculator truncates the ratio to two decimals instead of rounding, because 4.49:1 does not meet a 4.5:1 requirement. If a color sits on a gradient, image, or translucent layer, the CSS value is not the final color: sample the rendered pixel.

Severity scale

Rate severity by user impact on a real task, not by how hard the fix is.

LevelMeaningExample
S1 BlockerStops a user finishing a core task, or makes core content unreadable or unreachable.Primary button invisible in dark mode; keyboard trap in a dialog.
S2 MajorA significant barrier, but a workaround exists.Muted table text at 3:1; error shown by color only.
S3 MinorNoticeable, low impact, does not block anything.Inconsistent spacing; tooltip not dismissible.
S4 PolishRefinement with no real user impact.Icon weight differs between two screens.

WCAG 2.2 additions in this checklist

These criteria are new in WCAG 2.2, so older checklists and audit habits often miss them.

CriterionLevelIn plain termsChecklist item
2.4.11 Focus Not Obscured (Minimum)AAThe focused element is never entirely hidden behind sticky bars or banners.K5
2.5.7 Dragging MovementsAAAnything done by dragging also works with a single click or tap.K9
2.5.8 Target Size (Minimum)AAPointer targets are at least 24 by 24 CSS px, or spaced enough.K10
3.2.6 Consistent HelpAHelp or contact options sit in the same place across pages.N5
3.3.7 Redundant EntryADo not ask for information the user already entered in the same process.F7
3.3.8 Accessible Authentication (Minimum)AASign-in does not require memorizing or solving a puzzle; paste and password managers work.F8

Level AAA criteria, including 2.4.8 Location and 2.4.13 Focus Appearance, are out of scope. Where this checklist asks for something AAA-adjacent, such as marking the current nav location, it is tagged as a practice item.

DevTools methods

Chromium-based DevTools are described here. Firefox and Safari have close equivalents under their own names.

  • Sample a color. In the Styles pane, click a color swatch, then use the eyedropper to pick the rendered pixel. This is the right method for gradients, images, and translucent glass layers.
  • Emulate color scheme, reduced motion, forced colors, and vision deficiencies. Open the Rendering panel from the three-dot menu under More tools. Set the options you need, then reload.
  • Test widths. Use the device toolbar and set a custom width of 320, 375, 768, 1280, and 1920.
  • Throttle the network and CPU. In the Network panel pick Slow 4G, and use the Performance panel for CPU throttling.
  • Inspect accessible names and roles. Use the Accessibility pane in the Elements panel to see the computed name, role, and state of any element.
  • Check zoom. Browser zoom to 200% for text resize and 400% (or a 320px device width) for reflow.
